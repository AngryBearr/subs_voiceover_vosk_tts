# Память эксперимента сокращения субтитров

Последний человекочитаемый итог: [`shortening_results_2026-09-10.md`](shortening_results_2026-09-10.md). Проверенная компактная числовая сводка: [`expanded_comparison_final.json`](../output/shortening_verification_20260910/expanded_comparison_final.json).

Это рабочая запись для человека. Здесь разделены реализованные правила,
измеренные прогоны, ограничения и пока не проверенные гипотезы. Числа взяты из
первичных отчётов, а не из впечатления от отдельных фраз. `trial` ниже означает
«прогон», `unknown cost` — «неизвестный расход».

## 1. Что реализовано и какой вопрос проверяется

Цель — проверить, может ли LLM сократить субтитр, сохранив **полный смысл**:
сущности, числа, отрицания, модальность, время, причины, действующих лиц и
связи с соседними репликами. Допустима свободная перефразировка: совпадение
слов с оригиналом не является критерием. При этом смысловой вывод делает только
LLM-арбитр Sol; локальный код проверяет структуру, пустоту, Unicode-длину и
лимит символов, но не качество смысла. Человек не ранжирует получившиеся
субтитры вручную как «лучшие».

Для каждой цели генератор видит до трёх оригинальных реплик до неё и до трёх
после неё. Этот контекст является данными, а не инструкциями. Арбитр получает
отдельный свежий запрос и не видит имя генератора или его историю.

Основные ограничения планировщика:

- `max_speed = 1.5`, `gap_ms = 200`, а базовая эвристика — 13 символов в
  секунду. Это текстовый ориентир, не измеренный темп аудио.
- Пачка генерации — 6 целей, пачка проверки — 12 целей. По умолчанию разрешена
  одна исправляющая попытка и только для отклонённых/непринятых целей. Уже
  принятый результат окончателен и заново не «улучшается».
- Смысловая проверка — LLM-only: Sol выносит вердикт `accept`, `revise` или
  `impossible`. Локальная проверка не подменяет этот вердикт.
- В JSON сохраняются исходные позиции и индексы, включая повторяющиеся
  индексы. В SRT используется каноническая хронологическая нумерация. Исходные
  тайминги при этом не меняются.
- При ошибке транспорта, схемы, локальной проверки или модели действует
  fail-closed: в результат попадает оригинал, а запись и причина остаются в
  отчёте. После каждой пачки сохраняются checkpoint, `report`, субтитры и
  ledger запросов.
- К знаменателю политики 15% относятся выбранные записи с исходным превышением
  бюджета, а также выбранные `short_timing` и записи с ошибкой; нетронутые
  `fits` в него не входят. Ошибка остаётся отдельной инфраструктурной
  категорией, но не исчезает из знаменателя. Это правило ещё не доказывает,
  что 15% выполнены на полном файле.
- Короткие исходные случаи не заставляются переписывать только ради наличия
  кандидата. Решение `cannot_shorten` может оставить оригинал и направить запись
  на ручное рассмотрение.

Разрешённые режимы:

| Роль | Разрешённые режимы |
|---|---|
| Генератор DeepSeek Flash | `deepseek:off`, `deepseek:low`, `deepseek:high`, `deepseek:max`; Pro не используется |
| Генератор Luna через OAuth | `opencode:none`, `opencode:low`, `opencode:medium`, `opencode:high` |
| Арбитр | Sol, только `medium` |

Контекст и советы передаются структурированным JSON. Chain-of-thought не
сохраняется. `--length-tools` — необязательный инструмент точного локального
счётчика; его наличие само по себе не означает, что модель им воспользовалась.

## 2. Как запускать и где искать результат

Правильное окружение этого checkout — `subs_env`, а не `subs_venv`.
Команды запускаются из корня через `uv`. Сухой режим является значением по
умолчанию: он не делает сетевых запросов, не требует модели и сохраняет план и
manifest. `--execute` — явное согласие на живые запросы. Каталог результата не
перезаписывается; для нового прогона нужен новый путь.

Ниже только пример интерфейса; этот пример не запускался в рамках обновления
документации:

```bash
source subs_env/bin/activate
uv run --active --no-sync -m utils.shorten_subtitles \
  skill_test/S01_E01_ru_analyzed.json \
  --output-dir output/shortening_full_deepseek_low \
  --generator deepseek:low \
  --repetitions 1 \
   --per-severity 0 \
  --max-tokens 32768 \
   --execute
```

Здесь намеренно явно указаны `--generator`, `--repetitions 1` и
`--per-severity 0`: это полный файл для одного режима и одного повтора.
Если эти параметры не указать, CLI выбирает всю матрицу генераторов и два
повтора, что кратно увеличивает расход. `--execute` нельзя считать значением
по умолчанию.

Значение thinking по умолчанию `8192` ограничивает reasoning, а в эксперименте
использовался общий лимит `--max-tokens 32768`, включающий reasoning и ответ.
Больший лимит не гарантирует завершённый ответ: `high`/`max` всё равно
закончились по `finish_reason_length`. Полнофайловый пример выше не является
утверждением о production-ready готовности timing-профиля.

Основные точки кода:

- `utils/shortening_plan.py` — бюджеты, статусы и воспроизводимая выборка;
- `utils/shortening_prompts.py` — версия промпта `shortening-v1` и строгие
  схемы JSON;
- `utils/shortening_runner.py` — пачки, Sol, исправление, checkpoint и ledger;
- `utils/shortening_backends.py` — прямой DeepSeek и изолированный OpenCode;
- `utils/shortening_costs.py` — расчёт известного расхода и прогноза;
- `utils/shortening_timing.py` — диагностический профиль по WAV;
- `utils/shorten_subtitles.py` — dry/live CLI.

Результат одного прогона ищется в его `manifest.json`,
`experiment_summary.json`, `report.json`, `calls.jsonl`, `requests.jsonl` и
экспортированных JSON/SRT. В отчёте отдельно видны стадии
`generation`/`review`/`repair`/`recheck`, токены, исправления, известный
subtotal, неизвестные вызовы и hash-guards.

## 3. Что фактически проверено на текстовом эксперименте

Первичный источник числового сравнения —
[`comparison_verified.md`](../output/shortening_verification_20260909/comparison_verified.md)
и его [JSON](../output/shortening_verification_20260909/comparison_verified.json).
Проверка сделана по первичным `report`/`calls`/`requests`/`manifest` и полным
выходам, без изменения истории. Исходный файл содержит 839 записей, его SHA-256
`1cb82d7efa4036f6a7b3d324335ebd02b47168c3a017ebe10aa35d72d7ed4fb5`. Во всех
16 прогонах использованы те же 6 выбранных ID и сохранены индексы и тайминги:
это 8 настроек (4 Flash и 4 Luna) по 2 повтора, а не 16 независимых выборок.

### Принятые по смыслу и длине записи

Число ниже — итоговое `accept` после Sol и локальной проверки длины, из 6; в
скобках `[r1, r2]`. Это не ручная оценка и не ground truth.

| Генератор | Результат из 6 `[r1, r2]` | Что важно |
|---|---:|---|
| Flash `off` | `[5, 5]` | — |
| Flash `low` | `[6, 6]` | — |
| Flash `high` | `[0, 0]` | запросы закончились по `finish_reason_length` на лимите 32768 |
| Flash `max` | `[0, 0]` | запросы закончились по `finish_reason_length` на лимите 32768 |
| Luna `none` | `[6, 4]` | — |
| Luna `low` | `[5, 6]` | — |
| Luna `medium` | `[4, 6]` | — |
| Luna `high` | `[5, 4]` | — |

Для Flash `high`/`max` нет вердикта о смысле: ответ оборвался ограничением
длины. Нельзя называть это «плохим качеством». Повтор одного режима снова
использовал те же 6 уникальных записей, поэтому `[r1, r2]` не означает 12
независимых случаев. Доли отражают только решения Sol и не гарантируют
смысловую точность, победителя или выполнение 15% на полном файле.

В отчёте исправленный расчёт ledger получил 50 строк, неизвестных вызовов — 0;
все первичные отчёты имели полный учёт, а пересчитанные суммы совпали с
первичными в пределах `1e-10`. Это проверка чисел и структуры, не новая
семантическая оценка. Старое поле `cost_estimate` сохранено как сырое
свидетельство; для старых логов расчёт из `call_record_from_dict` и
`estimate_record_cost` является исправленным источником стоимости, но не
заменяет usage counts.

## 4. Что проверено по аудио и timing-профилю

Это отдельная проверка локального синтеза, не проверка смысла и не прослушивание.
Использовались `models/vosk-model-tts-ru-0.10-multi`, voice `8`, скорость
`1.5`, без пост-ускорения, `ruaccent`, нормализации числительных, удаления
тишины или другой обработки скорости.

### Нормализация пунктуации

Из 6 принятых записей Luna `low` r2 и 6 принятых Flash `low` r2 исходный TTS
прогон дал по 2 фактических попадания и по одной `SynthesisError` на каждый
набор. Добавлена только TTS-нормализация Unicode-кавычек, тире, многоточия и
пробелов к поддерживаемой пунктуации; отображаемый оригинал не изменяется.
После нормализации для каждого набора получены 12 WAV, ошибок синтеза — 0,
но фактических попаданий осталось 2/6. Это не основание заключать, что не
хватает модели, и не оценка семантики.

Первичный источник —
[`audio_normalized_verification.json`](../output/shortening_verification_20260909/audio_normalized_verification.json).

### Профиль лимита и follow-up

Добавлены явные интерфейсы `--timing-profile` и `--selection-manifest`:

- профиль строится по измеренным WAV и ограничивает символы через `floor`
  после margin `0.95`; второй множитель `1.5` не применяется;
- это эвристика длительности original/final, а не гарантия попадания в окно;
- профиль привязан к hash исходника и прогона, окну, voice и preprocessing;
- `--selection-manifest` замораживает выборку и не даёт незаметно сменить
  шесть записей.

В одном follow-up для Luna `low` caps изменились: `17→8`, `14→7`, `27→11`,
`23→14`. Sol принял 5/6, а аудио было измерено у 5 принятых: 2/5 попаданий,
то есть 2/6 при полном знаменателе. Три оставшиеся принятые короткие фразы
были двухсловными и имели перекрытия `0.200408`, `0.120907` и `0.251247` секунды;
все символы укладывались в новый cap. Одна запись осталась manual. Короткое
перекрытие не считается попаданием.

Источники follow-up:

- [`timing_followup_verification.json`](../output/shortening_verification_20260909/timing_followup_verification.json);
- [`output/shortening_timing_followup_20260909/`](../output/shortening_timing_followup_20260909/);
- [`output/shortening_audio_timing_followup_20260909/`](../output/shortening_audio_timing_followup_20260909/).

Наблюдение согласуется с гипотезой о коротких аудио-перекрытиях, но mixing и
ducking ещё не реализованы. Короткие фразы следует обрабатывать отдельной
аудио-политикой, а не бесконечно ужимать LLM-текст; зафиксированное решение:
короткие перекрытия помечены как `pending`, mixing/ducking намеренно отложены,
автоматическое изменение громкости не реализовано. Цель 15% end-to-end пока не
продемонстрирована: в маленьком примере manual был 1/6 (16.7%), а три случая
короткого аудио требуют отдельной политики.

## 5. Расход, журнал решений, источники и пределы уверенности

### Стоимость

Снимок тарифа DeepSeek сделан 2026-09-09 по официальному источнику
<https://api-docs.deepseek.com/quick_start/pricing>. Для этого снимка peak:
cache-hit `0.014`, cache-miss `0.44`, output `1.32` USD за миллион; off-peak:
`0.007`, `0.22`, `0.66`. Период выбирается по времени начала вызова. В
расчёте DeepSeek reasoning уже входит в output и не прибавляется второй раз.
Поля OpenCode показывают output и reasoning раздельно, поэтому нельзя
переносить правило DeepSeek на OpenAI общим утверждением.

Из первичных отчётов получены следующие usage-derived суммы. Это цена по
зафиксированному тарифу, не счёт-фактура:

- матрица Flash: `0.114170128` USD;
- два smoke-корня, прямые DeepSeek-вызовы: `0.01120894` USD;
- разведочный Flash с инструментом: `0.007338136` USD;
- известный subtotal этих оплаченных прямых экспериментов:
  `0.132717204` USD (примерно `$0.13`).

Для OpenAI были только OAuth-запросы через подписку: прямых платных API-запросов
`0`, quota и token usage записывались. `usage.cost = 0` — не настоящая API-цена
и не утверждение «бесплатно» или «безлимитно». Для сравнения человека с
платным API нужен фактический тариф Sol.

Прогноз на 500 записей применим **только** к прямой генерации DeepSeek и
исправлениям при условии, что Sol остаётся через подписку:

| Режим | Прогноз на 500 |
|---|---:|
| Flash `off` | `0.0368243333…–0.077702` USD (примерно `$0.04–0.08`) |
| Flash `low` | `0.633058333…–1.471219` USD (примерно `$0.63–1.47`) |

Сломанные `high`/`max` не имеют применимого прогноза и не являются дешёвым
сравнением сервиса. Прогноз предполагает около 6 стратифицированных записей с
разнесённым контекстом в пачке и реальные 500 разных текстов; cache и частота
исправлений могут измениться. Это не гарантия будущего расхода и не цена
полного стека OpenAI.

В таблице `comparison_verified` поле применимости означает именно наличие
расчётной базы: для Flash `off` и `low` оно истинно, для оборвавшихся `high` и
`max` — ложно. Нулевые строки Luna не являются прогнозом бесплатного API:
это OAuth usage без известного тарифа и без счёта-фактуры.

### Хронология журнала

Порядок зафиксированных этапов такой:

1. Нативный structured output в одном опыте не сработал: модель не вызвала
   нужный инструмент. Строгий plain JSON с локальным разбором решил транспортную
   проблему без хранения рассуждений.
2. Зафиксированы пределы reasoning `8192` и `32768` и повторён baseline с
   одинаковой шестёркой.
3. Проведён отдельный необязательный опыт `--length-tools`.
4. Добавлена TTS-нормализация пунктуации без изменения текста на экране.
5. Добавлен измеренный timing-профиль и follow-up через замороженный manifest.

Версия промпта `shortening-v1` и runtime-изменения — разные метки. Наличие
последующих исправлений транспорта не означает, что все промпты оптимизированы.

Каждая будущая запись должна содержать: путь к исходнику и hash; модель,
режим, seed, repetitions, batch sizes, token limit; наличие tool и profile;
фактические метрики, причины решения, полный путь к первичному отчёту и
неизвестные поля. Старые факты нельзя молча заменять новыми. Итоговое число
проверок финального набора здесь не заявляется: основной агент добавит его
после финального запуска, если он состоится.

## 7. Хронология и решения 2026-09-10

Это новая запись хронологии; прежние датированные факты выше не переписываются и не объявляются текущими задним числом.

Восемь ответов генерации на повтор для raw C посчитаны из завершённых уникальных запросов стадии `generation_candidates`; повторы являются стохастическими повторами, а не объясняются выдуманными retry.
